### 2.2 RewardVault Funding Procedure

The 15M PW allocation to `RewardVault` is NOT a genesis allocation — it is transferred post-deployment by the deployer using a separate funding key:

```solidity
// In DeployProduction.s.sol (executed after contract deployment)
rewardVault.fund{value: 15_000_000 ether}();
require(rewardVault.totalFunded() == 15_000_000 ether, "DEPLOY: underfunded");
```

**Hard invariant:** The deployment script reverts if `totalFunded != 15_000_000 ether` after the funding call.

## 5. Blockchain ID and Subnet ID

### Generation

The Blockchain ID and Subnet ID are generated by the Avalanche network when the subnet and blockchain are created. They cannot be predetermined.

**Process:**
1. Create subnet on Fuji testnet first (for rehearsal)
2. Note the Subnet ID and Blockchain ID from the testnet
3. Use testnet values in all non-production scripts
4. At mainnet ceremony: create subnet on mainnet, record real IDs
5. Update all configuration files with real IDs before bootstrapping validators

## 7. Immutability Consequences

**After the chain is bootstrapped, the following CANNOT be changed:**
- Genesis allocations (addresses and amounts)
- Chain ID (73571)
- NativeMinter configuration (disabled forever)
- Total supply (100M PW)
- Block gas limit (30M)
- Target block rate (2s)

**Post-deployment changes (via governance only, 48h timelock):**
- Emission rate (via RewardVault.setEmissionRate, capped at MAX_RATE_PER_SECOND)
- Validator weights (via registry admin)
- Keeper EOA (update KEEPER_PRIVATE_KEY, no contract change)
- EMS signers (deploy new EMS, setPauseController via timelock)
