6. FIRST TASK — MAP THE ACTUAL VALIDATOR ARCHITECTURE
============================================================

Before writing integration code, create a precise architecture map.

Determine:

A. Where validator identity exists.

B. Where validator membership is managed.

C. Where validator status exists.

D. Where validator weight exists.

E. Where validator uptime/eligibility exists.

F. Which layer owns each piece of information.

G. Which information is available to EVM contracts.

H. Which information is only available to the P-Chain.

I. Which information can be communicated securely across layers.

J. Whether PrimeWave can observe validator lifecycle events.

Create a table:

| Data | Source | Layer | EVM accessible? | Secure access method |
|------|--------|-------|-----------------|----------------------|

Do not guess.

============================================================
7. VALIDATOR IDENTITY
============================================================

Determine the canonical validator identity used by Avalanche.

Do NOT assume it is:

- an EVM address
- a normal Ethereum address
- a P-Chain address
- a reward recipient address

unless the source architecture proves it.

Define the mapping:

Avalanche Validator ID
        ↓
PrimeWave validator identifier
        ↓
Fee reward recipient

The mapping must be deterministic and auditable.

If one Avalanche validator can have multiple EVM reward addresses:

document how the relationship works.

If an EVM reward address is not inherently tied to validator identity:

document the secure binding mechanism.

============================================================
8. VALIDATOR LIFECYCLE
============================================================

Map the lifecycle:

Validator proposed/registered
        ↓
Validator active
        ↓
Validator weight/state changes
        ↓
Validator inactive/removed

Determine exactly how PrimeWave can detect each transition.

The accounting system must not continue allocating new fees to a validator that is no longer eligible.

Previously accrued fees must remain claimable according to C04 rules unless the protocol explicitly specifies otherwise.

============================================================
9. PHASE 1 POA MODEL
============================================================

C05 is primarily about Phase 1.

PrimeWave launches with:

15 initial PoA validators.

The C04 validator weights were development accounting parameters.

C05 must determine how the actual Phase 1 validator set can safely drive those accounting records.

For Phase 1:

- no staking
- no delegation
- no staking weight
- no staking rewards

The validator set is the source of validator eligibility.

============================================================
10. WEIGHT MODEL
============================================================

Do NOT invent a staking weight model.

For Phase 1 PoA:

the accounting system should use the approved equal-weight model unless Avalanche's actual validator-management semantics require a different representation.

Document:

- what "weight" means in Avalanche
- whether all 15 validators are equal
- whether validator weight can change
- who controls that change
- how a weight change affects accumulated fees

If Avalanche's validator manager does not expose an EVM-readable weight:

STOP before inventing a substitute.

============================================================
14. REWARD RECIPIENT SECURITY
============================================================

C04 has a rewardRecipient for each validator.

C05 must determine how the reward recipient becomes securely associated with the actual validator.

Potential attack:

Attacker registers:

Validator ID = legitimate validator
Reward recipient = attacker

This MUST NOT be possible.

The integration must prevent unauthorized reward-recipient reassignment.

If reward recipients are configured outside Avalanche's validator identity system:

document the secure registration/binding ceremony.

============================================================
15. VALIDATOR REGISTRATION
============================================================

Implement local registration integration only if technically supported.

For every validator registration verify:

- canonical validator identity
- reward recipient
- active status
- weight
- eligibility

Registration must not duplicate a validator.

Attempting to register the same validator twice must fail safely.

============================================================
16. VALIDATOR DEACTIVATION
============================================================

Test:

Validator becomes inactive.

Expected behavior:

- no new fee entitlement accrues after effective deactivation
- previously accrued entitlement remains claimable
- accounting state remains consistent
- validator identity remains historically traceable

Do NOT confiscate earned fees.

============================================================
17. VALIDATOR REACTIVATION
============================================================

If the underlying Avalanche architecture permits validator reactivation:

test:

inactive
→ active

Verify:

- new fee accrual resumes correctly
- old claim checkpoint is preserved
- no historical fees are double-counted

If reactivation is not applicable to the chosen Avalanche lifecycle:

document that instead.

============================================================
18. WEIGHT CHANGE
============================================================

If actual validator weight can change:

test:

Weight 1
→ Weight 2

The implementation must correctly checkpoint accumulated fees before applying the new weight.

Never retroactively apply a new weight to historical fees.

This is critical.

Example:

Period A:
weight = 1

Period B:
weight = 2

Fees earned in Period A must remain calculated using weight 1.
