Validator entitlement ∝
effective validator weight × eligibility/uptime

C04 must prove the accounting mathematics and security of this model.

============================================================

Before writing the accounting implementation, determine exactly how the validator identity and validator status will be represented.

PrimeWave currently has:

15 initial PoA validators.

The accounting system must NOT invent a second unrelated validator system that can disagree with Avalanche's actual validator set.

Determine:

A. How Avalanche identifies validators.

B. Whether those identifiers can be represented safely in the EVM accounting layer.

C. How the accounting layer will know:

- validator exists
- validator is active
- validator weight
- validator eligibility
- validator uptime

D. Which data is available directly on-chain.

E. Which data must be supplied by an authorized protocol component.

F. How the system prevents an unauthorized party from fabricating validator uptime or weight.

If an exact integration with Avalanche's Validator Manager cannot yet be implemented safely:

DO NOT fake it.

Build the accounting layer with a clearly defined interface/adapter boundary and document the integration requirement.

============================================================
8. RECOMMENDED ACCOUNTING MODEL
============================================================

Evaluate whether an accumulated-fee-per-weight / reward-index model is the most efficient architecture.

Conceptually:

Fee arrives
    ↓
ValidatorFeeVault
    ↓
Total eligible weight
    ↓
accumulatedFeePerWeight increases
    ↓
validator's effective weight
    ↓
validator claimable amount

For example:

accumulatedFeePerWeight +=
    feeAmount / totalEffectiveWeight

A validator's claimable amount is based on:

validatorWeight ×
(unclaimed accumulatedFeePerWeight)

Use integer fixed-point arithmetic.

Do NOT use floating-point arithmetic.

If another accounting model is demonstrably safer or simpler, use that instead and document why.

============================================================
9. NO O(N) DISTRIBUTION
============================================================

Do NOT distribute fees by looping over all 15 validators every time a transaction fee arrives.

That would unnecessarily increase gas and scale poorly.

Prefer:

Fee accumulation
→ global accounting index
→ individual validator claim

This should allow fee accounting to remain approximately O(1) for fee accrual.

Claims should be O(1) per validator.

============================================================
14. ROUNDING
============================================================

Native PW uses integer denomination.

Define deterministic rounding.

Do NOT allow rounding dust to disappear silently.

For every accounting period:

total validator allocations
<=
fee amount received

Any remainder must be explicitly:

- retained in the vault
- carried forward
- allocated according to a documented deterministic rule

Do NOT burn rounding dust unless explicitly approved.

Do NOT send rounding dust to Treasury.

Do NOT silently discard it.

============================================================
15. CLAIM MODEL
============================================================

Determine whether validators should:

A. Pull/claim their accrued fees

or

B. Receive automatic transfers.

Prefer the pull model unless there is a compelling reason otherwise.

Reasons:

- lower systemic gas cost
- no O(N) distribution
- validator chooses when to claim
- simpler accounting

A successful claim must:

1. calculate validator's claimable amount
2. update accounting checkpoint
3. transfer native PW
4. emit event
5. prevent double claiming

- modify its weight
- modify uptime

- withdraw vault funds directly
- redirect another validator's reward

Test all of these.
